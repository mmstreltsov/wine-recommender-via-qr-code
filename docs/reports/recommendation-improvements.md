Дата: 10.11.2026. Пользователь согласовал реализацию; выполнены реализация и проверки, перечисленные
ниже. Новая приёмка **не завершена**, RI-10 **PARTIAL** из-за открытого дефекта истории.
Исторические M1–M5 PASS не являются результатами этой работы.

## Решение И Скоуп

Цель: дополнения показываются раньше напитков/десертов, суп не получает одновременно хлеб и
хачапури, корзина учитывает весь доступный состав без автоматического второго основного,
а гость может изучить рекомендацию до добавления. Винный модуль, runtime LLM/ML, новые роуты,
платёжные/публичные deploy-операции не добавляются.

Канонические источники, без отдельных дублирующих SPEC/PLAN:

| Предмет | Спецификация |
|---|---|

Изменение сохраняет category-wise expert → upsell → heuristic в ForDish. Политика плагина
задаёт порядок фактических категорий, bakery-слот супа и роль substantial в файле
`recommendation_policy.json`.
Effective category по прежнему контракту category_override остаётся для каскада и принадлежности пары
курсу; фактическая категория используется для группировки/ролей/покрытия. Legacy override
fixture не отменяется. Неизвестная политике категория получает детерминированный fallback
перед десертами/напитками, а не исключается.

Для ForCart сохраняется прежний `forcart_priorities.json`, но рассматриваются все доступные
anchors и глобальный каскад внутри каждой недостающей группы. Unrestricted fallback удаляется;
ограниченный no-main разрешён лишь после исчерпания недостающих групп и лишь от фактических
гарнира/соуса/хлеба к substantial по существующей связи при отсутствии substantial в доступной
корзине. Недоступный anchor не даёт покрытия, его ID всё равно исключён. Availability цели
остаётся отдельным пост-фильтром без повторного поиска.

Last-item формулировка в историческом ADR-0004 описывает прежний ForCart и заменяется этой
редакцией `recommender.md`; решение ADR о no-runtime-LLM и статических текстах не меняется.

Открытие рекомендации использует только существующий `/dish/:id` и безопасный внутренний
history context. Новых имён событий нет, расширяется dish_card_open.source; detail-add
сохраняет source входа. Фото/текст-ссылка и добавление являются соседними элементами.

## Базовая Линия

- Матрица остаётся **414 expert-пар bytewise**, reason_text/score не редактируются. Меню,
  эвристики, upsell-маппинг и прежние приоритеты корзины не меняются.
- Историческая [сверка расширения](gastronomy-matrix-expansion.md) зафиксировала 414 карточек
  при полном меню/пустой корзине: 94×3 + 23×4 + 8×5. Это прежний алгоритм, не новая приёмка.
- Целевой baseline: **413 карточек**, 95×3 + 22×4 + 8×5; 125/125 лент сохраняют ≥3.
  Только грибная похлёбка `872278461583` сокращается 4→3: хлеб `496885548332` выигрывает
  bakery-слот у пеновани `188209721232`. Пара к пеновани не удаляется из матрицы.
- Пять целей хинкали `655892482392`, их тексты/score сохраняются; изменяется порядок
  по группам фактических категорий, а не содержимое экспертных пар.
- С исключениями корзины/наличия минимум три не обещается. Возврат к исходному входу
  восстанавливает ленту; нет постоянного удаления категории или replacement-поиска.
- Известный stale baseline: `backend/cmd/server/main_integration_test.go:820` ожидает для
  медовика `939802252842` одну рекомендацию и яблочный фреш первым. После расширения требуется
  **3** и новый порядок. Это задача обновления тестового ожидания, не повод удалять пары или
  менять тексты. На docs-шаге тест не исправлялся и integration не запускался.

## Результаты И Ограничения

- Backend: `go test ./...` и `go test -race ./...` PASS с доверенным `M2_IT_DATABASE_URL`,
  направленным с защитной проверкой в отдельную `m5_integration`; DB integration suite PASS.
  Вывод не подтверждает число выполненных DB-тестов. `go vet`, `golangci-lint` и валидатор
  матрицы PASS: 414 пар, покрытие 100%.
- Frontend: lint, 139 тестов npm и build PASS. При сборке шесть известных предупреждений о
  разрешении URL шрифтов во время выполнения; наличие шрифтов в mock-прогоне не гарантировано.
- Изолированный Vite с mock API, Playwright Chromium 158, 375/1440: 26 проверок, 0 ошибок.
  Проверены фото 4:3 над текстом, открытие по ссылке и source добавления, фактический refresh
  при отключённом Navigation API и восстановление `rec_cart` экранной кнопкой Back; наблюдались
  реальные impressions. Это mock API, не реальный backend; использованы локальные placeholder-фото.
- RI-10 **PARTIAL**: в браузерах без Navigation API после полной перезагрузки экранный Back
  использует безопасный replace fallback, но Forward не восстанавливает дочернюю страницу, а
  browser Back может попасть на дубликат родительской. Снимки ограничены четырьмя уровнями.
  Успешный сценарий восстановления `rec_cart` выше не закрывает этот дефект.
- Backend стека `vkr-dev` пересобран командой `docker compose up -d --build --no-deps backend`
  без удаления БД и volumes. `docker compose ps`: backend и db healthy, порты loopback
  `127.0.0.1:18080` и `127.0.0.1:55432`. `python3 scripts/smoke.py --base-url http://127.0.0.1:18080`
  PASS: health без создания сессии, SPA/deep links/assets, шесть шрифтов, CSP, nosniff и no-store.
- Физические Safari/iOS и Android не проверены. Сквозного браузерного прогона с реальным
  backend для этой редакции нет; smoke не является полной runtime/browser-приёмкой backend,
  результаты не означают полной приёмки, production или пилота.
- Контракты и документация согласованы архитектором, security, ревьюером требований и
  аналитиком. Статический security-аудит реализации PASS 0 CRITICAL / 0 HIGH / 0 MED / 0 LOW:
  read-only, без runtime-проверок и сканеров. Это не полный production-аудит.
- Независимый backend QA отметил эксплуатационное ограничение: семантическая валидация
  непустых пользовательских категорий и рангов обеспечивается, но редактирование policy может
  нарушить выбранные ранги/роли. Текущая предусмотренная конфигурация соответствует docs;
  произвольные изменения policy не получают дополнительной гарантии семантики.

Исторически на docs-шаге `git hash-object` до/после подтвердил bytewise-неизменность
matrix/heuristics/menu; тогда тесты и runtime не запускались. Это evidence того шага, а не
замена перечисленным выше проверкам реализации. Интеграционные проверки далее только на
disposable DB; рабочие данные и наличие не менять. Коммит и публичный деплой не выполнялись.
