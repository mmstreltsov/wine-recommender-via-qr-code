# ADR-0007: Публичный деплой пилота (VPS) и мультиресторанные URL

Дата: 2026-11-10 · Статус: принято, реализация отложена

## Контекст
Пилот с реальными гостями (АйДаБаран): QR на столике открывает сайт с телефона гостя.
Текущий стек — локальный прототип: compose публикует порты только на `127.0.0.1`
(`docker-compose.yml:10,24`), телефон ссылку открыть не может (корневой README:
«Loopback QR links cannot be opened from a guest's phone»). Origin-чек и Secure-cookie
рассчитаны на прямое TLS/HTTP-подключение (схема из `r.TLS`:
`backend/internal/api/mutation_guard.go:44-47`; `backend/internal/api/middleware.go:143`),
доверие к forwarded-заголовкам сознательно отсутствует после security-hardening M5.
Публичный TLS/прокси деплой объявлен в README отдельной последующей работой с новым
security-ревью. Ожидаемая нагрузка ≤5 RPS; анонимность без ПДн (ADR-0005).
Новое требование: потенциально несколько ресторанов и заведений — URL должен
идентифицировать ресторан и конкретное заведение.

## Решение
- **D1. VPS у RU-хостера** (Timeweb/Beget): 1 vCPU / 2 ГБ RAM / 20 ГБ NVMe, Ubuntu 24.04,
  вход только по SSH-ключу. Запас ×10–50 при 5 RPS; ~400–600 ₽/мес.
- **D2. Без Kubernetes и без балансировщиков нагрузки**: один docker compose на одной
  машине. Единственный L7-компонент — Caddy в роли TLS-терминации с автоматическим
  Let's Encrypt (0 ₽).
- **D3. Наружу только 22/80/443** (файрвол); backend и db во внутренней docker-сети,
  у db внешних портов нет. Публичный домен .ru (~200–900 ₽/год), A-запись → VPS; URL в QR
  постоянный. Бюджет инфраструктуры ~5–8 тыс. ₽/год.
- **D4. Обязательная доработка trusted-proxy в бэкенде — блокер деплоя**, реализация
  отложена: env `TRUSTED_PROXY_CIDRS`, доверять `X-Forwarded-Proto/Host/For` только от
  доверенных CIDR. Схему origin-чека брать из forwarded-proto (сейчас `r.TLS` —
  `backend/internal/api/mutation_guard.go:44`, иначе за прокси отвергаются все POST
  гостей); Secure cookie по итоговой схеме (сейчас `r.TLS != nil` —
  `backend/internal/api/middleware.go:143`); clientIP для rate-limiter из
  X-Forwarded-For доверенного прокси (сейчас `RemoteAddr` —
  `backend/internal/api/middleware.go:123`), иначе все гости делят IP прокси и
  коллективно упираются в лимит 30/мин → 429. Негативные тесты: поддельные
  forwarded-заголовки от недоверенных источников игнорируются.
- **D5. Мультиресторанные URL**: `https://menu.<домен>/?r=<ресторан>&v=<заведение>&table=N`.
  В v0 отсутствие r/v означает пилот по умолчанию (aidabaran); строгая валидация входных
  значений (недоверенные), неизвестные ID → 404 без деталей внутренней реализации.
  Печать QR отложена (число столов неизвестно) — схема URL фиксируется до первой печати,
  чтобы избежать перепечатки.
- **D6. Мультиресторанная переделка — отложено, в v0 не входит**: выбор плагина в
  рантайме по параметру URL (сейчас build-time `RESTAURANT=aidabaran`, registry в
  `backend/cmd/server/main.go:47/53`, см. ADR-0002); конфиг заведения (планируемый
  `data/<restaurant>/venues.json`: имя, число столов, тема); restaurant/venue в
  sessions/events (сейчас только `table_id *int`) и в колонках export CSV;
  `/api/v1/config` по заведению; валидация новых параметров в scripts/qr-seed.
- **D7. Фото** (~89 МБ, `data/aidabaran/photos/`) не в git: переносить rsync на VPS,
  иначе деградация к placeholder (FR-26).
- **D8. Эксплуатация**: pg_dump по cron (umask 077, ограниченный retention),
  availability/export-events по корневому README; обновление = `git pull` +
  `docker compose up -d --build`. Локальный LAN-демо-сценарий (временный
  `docker-compose.override.yml` с привязкой порта к LAN-IP, не коммитить) остаётся
  способом «открыть с телефона, когда развернуто на ноуте»; HTTPS-туннели
  (ngrok/cloudflared/tailscale serve) с текущим origin-чеком не работают — корзина
  ломается.

## Отвергнутые альтернативы
- Только Wi-Fi ресторана (LAN, без интернета): гость с мобильным интернетом не попадёт;
  подключение к чужому Wi-Fi — барьер; нужна всегда включённая машина на месте.
- HTTPS-туннели (ngrok, cloudflared, tailscale): терминируют TLS и шлют бэкенду HTTP —
  origin-чек отвергает записи (README: arbitrary TLS-terminating proxy forwarding HTTP
  will reject browser writes).
- Kubernetes / managed K8s / HAProxy-кластеры: цена (+5–10 тыс. ₽/мес) и операционная
  сложность без выигрыша в доступности — PG с volume живёт на одном хосте; при 5 RPS
  балансировать нечего.
- Path-based URL `/r/<id>/...`: подкаталоги SPA не поддерживаются
  (scripts/qr-seed/README.md), больше переделок роутинга; query-параметры совместимы
  с текущей раздачей статики.
- Отдельный деплой/домен на каждый ресторан: противоречит ADR-0002 (отдельные сервисы
  на ресторан уже отвергнуты), операционная сложность.

## Последствия и ограничения
- Этим ADR не вводится никаких изменений кода/compose: статус «решения приняты,
  реализация отложена».
- Реализация — отдельная мини-веха с обязательным независимым security-аудитом
  изменённого diff; обход guards (переписывание Origin, ослабление проверок) запрещён;
  доверенные forwarded-заголовки только от явно перечисленных CIDR.
- Прототип ВКР: публичный TLS/пилот вне скоупа M5 (README), production-гарантии
  не заявляются.
- Схему URL зафиксировать до печати QR-стойки.
