# ADR-0006: Учёт наличия блюд (availability)

Дата: 2026-11-07 · Статус: принято

## Контекст
Онлайн-меню (125 позиций из `menu.json`) заметно больше фактического предложения зала —
выяснено визитом в пилотный ресторан: часть позиций отсутствует в конкретную смену. Гость
должен видеть, заказывать и получать рекомендации только по тому, что реально есть. Нужны
оперативные скрытия без релиза и без рестарта сервера во время смены.

## Решение
- Хранение — Postgres, таблица `item_availability` (`item_id BIGINT PK`, `is_available
  BOOLEAN NOT NULL`, `updated_at`). Семантика default-available: нет строки = позиция
  доступна (сейчас всё доступно, отключения внесёт заказчик позже). Без FK: меню — статика
  в памяти; `item_id` валидируется CLI против меню из `DATA_DIR`.
- Чтение — in-memory TTL-кэш на сервере (множество недоступных `item_id`), env
  `AVAILABILITY_TTL_S` (по умолчанию 5 с): изменения подхватываются без рестарта в
  пределах TTL.
- Управление — CLI-подкоманда того же бинаря: `availability set <item_id> on|off` (upsert) и
  `availability list`, по образцу `export-events`. «Соседний админский процесс»: работает с
  той же БД при живом сервере, без HTTP.
- Применение — фильтр по всем выдачам (меню, карточки, рекомендации, корзина — FR-37);
  в рекомендациях фильтр строго после каскада (матрица/эвристики не меняются).

## Отвергнуто
- Статический конфиг-файл в `data/` с применением рестартом — неоперативно, рестарт во
  время смены.
- Админ-UI / HTTP-эндпоинты управления — вне v0 (расширение поверхности атаки).
- Хранить availability в `menu.json` — смешение контента и операционного состояния, ломает
  ADR-0003.

## Последствия
- Матрица/валидатор (M1) не зависят от наличия: проверяются против полного меню.
- Будущий админ-интерфейс подключается к той же таблице `item_availability` (источник один).
- События аналитики не меняются: availability — не событие гостя.
