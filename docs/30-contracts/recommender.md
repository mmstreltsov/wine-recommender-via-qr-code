# 30.3. Контракт: реком-движок

Ядро знает только интерфейс (`20-architecture.md` §3). Всё нижеследующее — специфика
плагина `plugins/aidabaran` и его данных, но контракт типов/поведения общий для будущих ресторанов.

Редакция 10.11.2026: согласованная post-M5 цель, реализация и новая приёмка ещё не выполнены.
Исторические PASS M1–M5 не подтверждают новые правила; pending-критерии и границы изменения:

## 1. Поведение

### ForDish(itemID, excludeInCart) → []Rec (FR-10)
Кандидатные категории = все категории, кроме категории самого блюда.
Для каждой категории-кандидата выбрать топ-1 позицию по каскаду:

1. **Expert** — прямая пара в `matrix.json` (`dish_id = itemID`, пара относится к категории-кандидату —
   семантика `category_override` в §2): берём её, `source="expert"`, score = из матрицы. Если пар
   в категории-кандидате несколько — пара с max(score), при равенстве — меньший SortOrder rec_id,
   затем меньший rec_id.
2. **Upsell** — если у блюда есть `upsell_options`, а позиция-опция распознана маппингом в меню
   (см. §4) и лежит в категории-кандидате: `source="upsell"`, score 0.6. Несколько распознанных
   опций внутри одной категории-кандидата — берётся первая по порядку в `upsell_options`
   (детерминизм).
3. **Heuristic** — правило сочетания категорий (§3) подходит: топ позиции категории-кандидата
   (минимальный SortOrder), `source="heuristic"`, score 0.4.

Каскад внутри каждой категории не меняется, включая effective category из `category_override`
(§2). Категория самого блюда исключается по её фактическому ID. После каскада исключить
`excludeInCart` и сам itemID; если выбранный топ-1 исключён, категория гаснет без поиска
следующей пары/опции/позиции. Другие позиции той же категории в корзине сами по себе не
запрещают категорию. Availability остаётся отдельным пост-фильтром без замены.

К оставшимся кандидатам применить политику плагина (§1.1), не изменяя score/reason_text:

- Для источника фактической категории «Супы» кандидаты «Тандырный хлеб» и «Хачапури» занимают
  один bakery-слот. Предпочесть хлеб, затем score DESC → effective category ID ASC → SortOrder
  позиции ASC → item ID ASC. Любая позиция этой bakery-группы в `excludeInCart` подавляет слот
  целиком, даже если это не выбранный кандидат. Группа не включает «Чебуреки»; для других
  источников такого объединения нет. Подавленный слот не заменяется другой категорией.
- Финальный порядок по фактической категории цели: соусы → хлеб/малые гарниры → закуски/салаты
  → сытные курсы → неизвестная категория → десерты → напитки. Внутри уровня: score DESC →
  effective category ID ASC → SortOrder позиции ASC → item ID ASC. Неизвестная политике
  категория не теряется: детерминированный общий уровень перед десертами и напитками.
- Ограничение остаётся ≤ 13 позиций (14 категорий − 1). При полном меню и пустой корзине
  ожидаются ≥3 карточек для каждого из 125 источников, суммарно **413** карточек: 95 лент по 3,
  22 по 4, 8 по 5. Только грибная похлёбка `872278461583` сокращается с 4 до 3 (хлеб вместо
  одновременных хлеба и хачапури); матрица сохраняет **414 пар**. Исключения/наличие могут
  уменьшать ленту ниже трёх; восстановление исходного входа восстанавливает ленту.

### 1.1. Политика плагина

Категории, их группы показа, bakery-группа и роль `substantial` принадлежат плагину, не core
и не фронтенду. Предложенный новый источник данных: `data/aidabaran/recommender/recommendation_policy.json`;
физический формат и способ передачи в backend выбирает backend-исполнитель до реализации.
Контракт фиксирует семантику, не JSON-форму и не изменение публичного API.

| Группа показа (раньше → позже) | Фактические категории пилота |
|---|---|
| Соусы | Соусы |
| Хлеб / малые гарниры | Тандырный хлеб; Овощи на углях и гарниры |
| Закуски / салаты | Салаты; Холодные закуски; Горячие закуски |
| Сытные курсы | Супы; Хачапури; Хинкали; Чебуреки; Основные блюда; Блюда на углях |
| Общий fallback | Категория, не описанная в политике, до десертов/напитков |
| Десерты | Десерты |
| Напитки | Напитки |

Группа показа не равна роли насыщения: `substantial` = «Хачапури», «Хинкали», «Чебуреки»,
«Основные блюда», «Блюда на углях». «Супы» автоматически эту роль не получают. Для отдельных
«Горячих закусок» допустимы только явно отрецензированные UID-исключения в политике; угадывать
роль по названию/описанию нельзя. Категории/UID конфигурации валидируются против полного меню,
противоречивые назначения отвергаются. Неизвестная политике категория меню допустима и получает
общий fallback, а не угаданную роль. Матрица, тексты/score, меню, эвристики и
`forcart_priorities.json` в этой работе не меняются.

Effective category сохраняет своё назначение в каскаде и проверке принадлежности пары
категории/курсу. Группировка показа, bakery, покрытие корзины и роль `substantial` определяются
по фактической категории позиции (и только явным UID-исключениям для роли). Допустимый legacy
fixture с несовпадающим `category_override` не становится ошибкой и не переписывается молча.

### ForCart(lines, excludeInCart) → *Rec (FR-19/20/21)
1. Все доступные позиции корзины — anchors. Недоступные линии остаются в корзине и множестве
   исключённых ID, но не являются anchors, не покрывают группы и не дают роль `substantial`.
   Если доступных anchors нет — `nil`. Все ID корзины и `excludeInCart` запрещены как цели.
2. Покрытие считать по фактическим категориям доступных линий: группа покрыта любой позицией
   из неё. Приоритеты существующего `forcart_priorities.json` НЕ меняются: «Напитки» → «Десерты»
   → [«Салаты», «Холодные закуски»] → [«Овощи на углях и гарниры», «Соусы»]. Для каждой
   непокрытой группы по этому порядку выполнять глобальный каскад шага 3. Нет допустимого
   кандидата во всей группе — перейти к следующей непокрытой, а не сразу вернуть `nil`.
3. В пределах одной группы **expert по всем anchors → upsell по всем anchors → heuristic по
   всем anchors**, не полный каскад отдельно для каждого anchor. Для expert принадлежность
   группе определяется effective category (§2), для upsell/heuristic — категорией цели.
   Порядок expert: score DESC → индекс anchor DESC (новейший первым) → SortOrder цели ASC →
   target ID ASC. Повторный target ID от нескольких anchors дедуплицируется; сохранить
   выигравшую пару целиком, включая её reason_text, без смешивания текстов и score.
   Upsell: индекс anchor DESC → исходный порядок `upsell_options` (стабильный маппинг).
   Heuristic: индекс anchor DESC → ID разрешённой категории ASC → её топ-1 (SortOrder ASC →
   target ID ASC). Только существующие пары/маппинги/правила, без синтеза связей.
4. Если в доступной корзине уже есть `substantial`, другую `substantial`-цель отсеять ПРИ
   выборе, во всех источниках: можно продолжить поиск допустимой пары/опции/категории.
   Исключения ID также применяются при выборе expert/upsell. Для heuristic исключённый или
   запрещённый топ-1 гасит категорию целиком; второй элемент категории не берётся.
5. После исчерпания всех непокрытых групп (или если все покрыты) не выполнять старый
   unrestricted fallback. Единственное ограниченное дополнение: если в доступной корзине
   НЕТ `substantial`, искать только `substantial`-цель и только от anchors фактических
   категорий «Овощи на углях и гарниры», «Соусы», «Тандырный хлеб». Тот же глобальный каскад
   и tie-break шага 3, только через уже разрешённые expert/upsell/heuristic-связи. Нет такого
   anchor/связи — `nil`; суп/напиток/десерт сами не разрешают этот no-main fallback.
6. Вернуть одну рекомендацию либо `nil`: нормальны завершённый заказ, исчерпание допустимых
   связей, пустая/полностью недоступная корзина. Недоступность выбранной ЦЕЛИ по-прежнему
   проверяется только пост-фильтром ядра: удалённый кандидат → `null` без новой попытки по
   anchor/группе/каскаду/fallback (см. ниже). Это не правило пропуска недоступных anchors.

Индекс anchor — индекс в исходном порядке lines от репозитория (`added_at` ASC); фильтрация
недоступных не меняет относительный порядок. Новейший = наибольший индекс, не максимальный
UID. Повторный POST существующей позиции `added_at` НЕ обновляет (только `updated_at` корзины).
Одинаковый вход → одинаковый выход, без рандома.

### Доступность кандидатов (FR-36/37)
Недоступные позиции (`is_available=false`) исключаются из кандидатов ПОСЛЕ каскада — общее
правило для всех трёх источников (expert/upsell/heuristic) и обоих методов (ForDish-лента,
ForCart): фильтр — пост-обработка выдачи на уровне ядра (TTL-кэш наличия, `20-architecture.md`),
граф матрицы и правила эвристик НЕ меняются. Лента/кандидат опустели после фильтра → блок
скрывается (FR-29). Замена недоступного кандидата следующим по каскаду НЕ ищется: недоступный
топ-1 исключает категорию из ленты целиком. Детерминизм сохраняется. Матрица и валидатор (§2)
проверяются против ПОЛНОГО меню: срез доступности не применяется (наличие — операционное
состояние, не контент).

## 2. Файл матрицы `data/aidabaran/recommender/matrix.json`

```json
{
  "version": 1,
  "pairs": [
    {
      "dish_id": 366609864022,          // базовая позиция (uid из menu.json)
      "rec_id":  329216982342,          // рекомендуемая позиция («Сацебели»)
      "category_override": "Соусы",     // опц.: подсказка, к какой категории-кандидату пара относится
      "score": 0.9,                     // 0..1
      "source": "expert",
      "reason_text": "К острому ореховому салату — освежающий томатный соус с кинзой: он сбалансирует жирность и повторит травяную ноту."
    }
  ]
}
```
Семантика `category_override`: пара относится к категории `category_override`, если поле задано
и категория существует в меню, иначе — к категории `rec_id`. Override, не совпадающий с категорией
`rec_id`, — допустим, но валидатор выдаёт WARN.

Валидатор `cmd/validate-matrix` (CLI, веха M1): exit 0 — ок; иначе exit 1 и построчные ошибки.
Формат: matrix — `ERROR <rule> dish_id=X rec_id=Y: <детали>`; heuristics.json —
`ERROR heuristics from="X": <детали>`; upsell_map.json — `ERROR upsell_map text="...":
item_id не найден`; forcant_priorities.json — `ERROR forcart_priorities category="X":
нет в меню | более одной группы`. Проверки:
- все `dish_id`/`rec_id` существуют в меню; `dish ≠ rec`;
- `score ∈ [0,1]`; `reason_text` 60–220 символов, без стоп-слов («вкусно», «попробуйте» и
  популярные фразы из §5);
- покрытие: < 80% блюд с ≥ 1 парой → ERROR (exit 1); при покрытии ≥ 80% — список непокрытых
  блюд печатается как WARN, exit 0;
- каждая категория меню — целевая (rec_id) хотя бы 1 раз;
- все item_id в `upsell_map.json` существуют в меню;
- `forcart_priorities.json`: все имена категорий существуют в меню; каждая категория входит
  не более чем в одну группу (категории вне групп не образуют отдельный «недостающий курс» —
  оставаться вне групп допустимо; выбор цели определяется effective category и ограниченным
  no-main fallback §1, без отмены допустимого `category_override`).
Обратные пары не обязательны (матрица направленная).

## 3. Эвристики сочетания категорий (данные плагина, грузинская кухня)

Источник правды — `data/aidabaran/recommender/heuristics.json` (14 правил; не хардкод в Go).
Валидатор M1: каждая категория меню имеет ≥1 from-правило; все from/to-имена существуют в меню.
```json
{ "rules": [
  { "from_category": "Супы",     "to_categories": ["Хачапури", "Чебуреки", "Тандырный хлеб"] },
  { "from_category": "Хачапури", "to_categories": ["Салаты", "Холодные закуски", "Соусы"] },
  { "from_category": "Хинкали",  "to_categories": ["Холодные закуски", "Салаты", "Соусы"] },
  { "from_category": "Блюда на углях",      "to_categories": ["Овощи на углях и гарниры", "Соусы", "Салаты"] },
  { "from_category": "Основные блюда",      "to_categories": ["Соусы", "Овощи на углях и гарниры", "Десерты"] },
  { "from_category": "Салаты",   "to_categories": ["Горячие закуски", "Основные блюда"] },
  { "from_category": "Холодные закуски",    "to_categories": ["Основные блюда", "Блюда на углях"] },
  { "from_category": "Горячие закуски",     "to_categories": ["Салаты", "Напитки"] },
  { "from_category": "Чебуреки", "to_categories": ["Салаты", "Напитки"] },
  { "from_category": "Десерты",  "to_categories": ["Напитки"] },
  { "from_category": "Напитки",  "to_categories": ["Десерты", "Холодные закуски"] },
  { "from_category": "Овощи на углях и гарниры", "to_categories": ["Основные блюда", "Блюда на углях"] },
  { "from_category": "Соусы",    "to_categories": ["Хачапури", "Тандырный хлеб"] },
  { "from_category": "Тандырный хлеб",           "to_categories": ["Супы", "Соусы"] }

```
Отсутствие правила для пары категорий = heuristic-кандидат не даётся (expert/upsell всё равно
работают). Правила редактирует аналитик, код их только исполняет.

## 4. Upsell-маппинг (`upsell_options` → item_id)

Строка апсейла («Тигровые креветки (50г) 420₽») ≠ название позиции меню. Плагин держит ручной
словарь маппинга `upsell_text → item_id` (заполняется на M1 по факту). Файл:
`data/aidabaran/recommender/upsell_map.json`.

Ключи `upsell_map.json` — исходные тексты апсейлов с ценой (как в `menu.json`). Сопоставление
выполняет плагин при загрузке данных: ключ карты сопоставляется с `upsell_options[].name` после
нормализации обеих сторон (отрезание хвостовой цены regexp'ом из `data-model.md` §3 + trim);
результат — отображение item_id блюда → item_id опции для каскада. Несопоставленные опции
игнорируются.

## 5. Тексты обоснований (FR-11/12) — чек-лист стиля

- Гастрономическая причина: вкус/текстура/температура/контраст/региональная логика.
- Привязка к конкретному блюду («к копчёной скумбрии…»), не универсальная фраза.
- Тон высокой кухни, без канцелярита; 1–2 предложения (60–220 символов); без «вкусно», «попробуйте», смайлов.
- Референсные примеры:
  - ✅ «Ядрёный чабер и сулугуни в хачапури раскрываются с кислой вишней ткемали — соус срезает сливочность и оставляет томлёную корочку во вкусе.»
  - ✅ «К нежному пюре из щучьих котлет — хрустящий огурец и зелень: контраст текстур делает горячее легче и длиннее по послевкусию.»
  - ❌ «Это блюдо отлично сочетается с выбранным.»
  - ❌ «Популярный выбор гостей.»
Шаблоны эвристики (`texts.go`) подставляют названия и строят текст по схеме
«[блюдо] + [причина из правила] + [эффект]»; каждое правило несёт свой шаблон-фразу.

Тексты пар (`reason_text`) готовятся ЗАРАНЕЕ (M1): черновики генерирует LLM оффлайн по этому
чек-листу → пакетное ревью → валидатор (длина 60–220, стоп-слова, coverage). В v0 (MVP) в
рантайме LLM не используется — движок только выбирает пару и отдаёт готовый текст (решение
скоупа v0, ADR-0004; рантайм-LLM — допустимая опция v1+, контракт API при этом не меняется).

## 6. Что движок НЕ делает
- Не смотрит в wine/barmenu данные (v0), не генерирует тексты в рантайме, не хранит состояние,
  не читает БД (вход — аргументы), не зависит от HTTP.
