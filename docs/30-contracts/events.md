# 30.4. Контракт: события (аналитика исследования)

Цель: восстановить воронку гостя и ответить на вопросы исследования (кто сканировал, кто открыл
карточку, кто видел рекомы, кто добавил по рекомендации, кто дошёл до оплаты) + A/B по столикам.

## 1. Принцип разделения источников (кто пишет событие)

- **Сервер** пишет события API-действий автоматически (истина в БД, клиенту доверять нельзя).
- **Фронт** шлёт события UX (просмотры/показы/клики по интерфейсу) через `POST /api/v1/events`.

Дублирования нет: каждое событие имеет ровно один источник (таблица ниже).

## 2. Таксономия (AN-01: других имён не существует)

| name | Источник | Когда | Payload (обязательное в {}) |
|---|---|---|---|
| `page_open` | фронт | первый рендер SPA (одно `page_open` на загрузку документа; refresh = новое событие) | `{}` (table_id берётся сервером из сессии) |
| `menu_view` | фронт | меню отрисовано (данные загружены) | `{}` |
| `category_select` | фронт | выбран чип категории | `{"category_id": int}` |
| `dish_card_open` | фронт | открыта карточка блюда | `{"item_id": id, "source": "menu"}` |
| `rec_feed_visible` | фронт | блок рекомов карточки попал во viewport (≥50%); 1 раз в рамках одного открытия карточки блюда, повторное открытие — новое событие | `{"dish_id": id, "recs_count": int}` |
| `rec_impression` | фронт | карточка рекома попала во viewport (≥50%); дедупликация — в рамках одного открытия карточки блюда (ключ dish_id + монотонный счётчик открытий; повторное открытие карточки генерирует новые rec_impression для показанных рекомов) | `{"context": "dish"\|"cart", "rec_item_id": id, "rec_source": str}` |
| `menu_add_click` | сервер | `POST /cart/items` с `source=menu` | `{"item_id": id}` |
| `rec_add_click` | сервер | `POST /cart/items` с `source=rec_feed\|rec_cart` | `{"item_id": id, "context": "dish"\|"cart"}` |
| `cart_open` | фронт | открыт экран корзины | `{"lines_count": int, "total": int}` |
| `cart_qty_change` | сервер | `PATCH /cart/items/{id}` | `{"item_id": id, "from": int, "to": int}` |
| `cart_item_remove` | сервер | `DELETE /cart/items/{id}` | `{"item_id": id}` |
| `pay_click` | фронт | клик «Оплатить» (до перехода на заглушку) | `{"total": int, "lines_count": int}` |
| `stub_view` | фронт | открыт экран-заглушка | `{}` |

Ограничения payload: строго плоский JSON (только скалярные значения верхнего уровня, глубина 1),
≤ 1 КБ, только поля из таблицы (сервер валидирует имя и плоскость, типы полей — «best effort»,
события не должны ломать UX).

## 3. Воронка исследования (канонический порядок)

```
page_open → menu_view → dish_card_open → rec_feed_visible → rec_impression
           → rec_add_click/menu_add_click → cart_open → pay_click → stub_view
```
Воронка `page_open → menu_view` читается по сессиям, а не по событиям.
Ключевые метрики из данных:
- **Скан→интерес**: page_open / menu_view
- **Интерес→рассмотрение**: dish_card_open / menu_view
- **Конверсия рекомендации**: rec_add_click / rec_impression (главная метрика гипотезы
  С.2 — конверсия рекомендации в заказ)
- **Дозаказ**: сессии с ≥2 add_click (добавления после первого) / все сессии с add_click
- **A/B по столикам**: срез по table_id (table_id NULL = вне эксперимента)

## 4. Выгрузка (AN-04)

```bash
go run ./cmd/server export-events --from 2026-11-10 --to 2026-11-20 > events.csv
```
CSV: `ts,session_id,table_id,name,payload` (payload — JSON-строка в кавычках, RFC4180), UTF-8.
`--from`/`--to` — даты UTC, включительно; `ts` в CSV — ISO 8601 UTC; сортировка по ts, затем по id.
Без HTTP-эндпоинта (без auth-поверхности).

## 5. Приватность
- payload не содержит свободного ввода (его в v0 нет), имён, устройств, гео (AN-05).
- session_id — случайный UUID; table_id — номер столика (не персональные данные).
- Ретеншн: события храним бессрочно в рамках учебного проекта; чистка — решение later.
