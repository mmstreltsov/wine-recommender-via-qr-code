# 30.4. Контракт: события (аналитика исследования)

Цель: восстановить воронку гостя и ответить на вопросы исследования (кто сканировал, кто открыл
карточку, кто видел рекомы, кто добавил по рекомендации, кто дошёл до оплаты) + A/B по столикам.

## 1. Принцип разделения источников (кто пишет событие)

- **Сервер** пишет события API-действий автоматически (истина в БД, клиенту доверять нельзя).
- **Фронт** шлёт события UX (просмотры/показы/клики по интерфейсу) через `POST /api/v1/events`.

Дублирования нет: каждое событие имеет ровно один источник (таблица ниже).

## 2. Таксономия (AN-01: других имён не существует)

| name | Источник | Когда | Payload (обязательное в {}) |
|---|---|---|---|
| `page_open` | фронт | первый рендер SPA (одно `page_open` на загрузку документа; refresh = новое событие) | `{}` (table_id берётся сервером из сессии) |
| `menu_view` | фронт | меню отрисовано (данные загружены) | `{}` |
| `category_select` | фронт | выбран чип категории | `{"category_id": int}` |
| `dish_card_open` | фронт | открыта карточка блюда из меню либо рекомендации; source сохраняется в контексте входа | `{"item_id": id, "source": "menu"\|"rec_feed"\|"rec_cart"}` |
| `rec_feed_visible` | фронт | наблюдаемая область начала блока рекомов карточки попала во viewport (≥50%); 1 раз в рамках одного открытия карточки блюда, повторное открытие — новое событие | `{"dish_id": id, "recs_count": int}` |
| `rec_impression` | фронт | карточка рекома попала во viewport (≥50%); дедупликация — в рамках одного открытия карточки блюда (ключ dish_id + монотонный счётчик открытий; повторное открытие карточки генерирует новые rec_impression для показанных рекомов) | `{"context": "dish"\|"cart", "rec_item_id": id, "rec_source": str}` |
| `menu_add_click` | сервер | `POST /cart/items` с `source=menu` | `{"item_id": id}` |
| `rec_add_click` | сервер | `POST /cart/items` с `source=rec_feed\|rec_cart` | `{"item_id": id, "context": "dish"\|"cart"}` |
| `cart_open` | фронт | открыт экран корзины | `{"lines_count": int, "total": int}` |
| `cart_qty_change` | сервер | `PATCH /cart/items/{id}` | `{"item_id": id, "from": int, "to": int}` |
| `cart_item_remove` | сервер | `DELETE /cart/items/{id}` | `{"item_id": id}` |
| `pay_click` | фронт | клик «Оплатить» (до перехода на заглушку); при блокировке оплаты из-за недоступных линий (UI-04, FR-37) событие НЕ шлётся | `{"total": int, "lines_count": int}` |
| `stub_view` | фронт | открыт экран-заглушка | `{}` |

Ограничения payload: строго плоский JSON (только скалярные значения верхнего уровня, глубина 1),
≤ 1 КБ, только поля из таблицы (сервер валидирует имя и плоскость, типы полей — «best effort»,
события не должны ломать UX).

### Post-M5: навигация по рекомендации (AN-02)

Согласованная цель, новая приёмка pending. Новых имён событий нет: расширяется только
закрытый enum `dish_card_open.source`. Клик по фото/тексту RecCard открывает существующий
`/dish/:id`: из ленты блюда `rec_feed`, из рекомендации корзины `rec_cart`; из меню `menu`.
Контекст входа сохраняется при Back/refresh через безопасный внутренний history state;
прямой вход/новая вкладка без такого state → `menu`. Новая карточка имеет свою ленту:
переход из неё задаёт `rec_feed` независимо от предыдущего источника. Правила возврата,
валидации state и восстановления фокуса/скролла: `40-frontend.md`.

Кнопка добавления самой позиции в detail отправляет сохранённый source в `POST /cart/items`;
кнопка-сосед ссылки на RecCard отправляет источник своей текущей ленты/корзины, не открывает
detail и не порождает `dish_card_open`. `menu_add_click`/`rec_add_click` всё ещё пишет ТОЛЬКО
сервер по POST, без дубликатов с клиента; `context` add-события соответствует source
(`rec_feed` → `dish`, `rec_cart` → `cart`). Метрики различают просмотр detail и добавление.

Крупные фото не должны делать порог ≥50% недостижимым: геометрия/наблюдаемая область RecCard
и блока ленты должны допускать его достижение на 375px, в том числе для длинного обоснования.
Порог и дедупликация сохраняются; события не отправляются до фактической видимости. Повторное
открытие detail (включая Back) создаёт новый контекст показов, source входа при этом сохраняется.

## 3. Воронка исследования (канонический порядок)

```
page_open → menu_view → dish_card_open → rec_feed_visible → rec_impression
           → rec_add_click/menu_add_click → cart_open → pay_click → stub_view
```
Воронка `page_open → menu_view` читается по сессиям, а не по событиям.
Ключевые метрики из данных:
- **Скан→интерес**: page_open / menu_view
- **Интерес→рассмотрение**: dish_card_open / menu_view
- **Конверсия рекомендации**: rec_add_click / rec_impression (главная метрика гипотезы
  С.2 — конверсия рекомендации в заказ)
- **Дозаказ**: сессии с ≥2 add_click (добавления после первого) / все сессии с add_click
- **A/B по столикам**: срез по table_id (table_id NULL = вне эксперимента)

## 4. Выгрузка (AN-04)

```bash
go run ./cmd/server export-events --from 2026-11-10 --to 2026-11-20 > events.csv
```
Без HTTP-эндпоинта (без auth-поверхности). Правила:

- Колонки `ts,session_id,table_id,name,payload`; строка заголовка обязательна; пустая выборка →
  только заголовок, exit 0.
- `--from`/`--to` опциональны по отдельности: нет флага — граница открыта; оба есть — диапазон.
  Формат дат строго `YYYY-MM-DD`; день `--to` входит включительно (полуинтервал):
  `--from 2026-11-01` → `ts >= 2026-11-01T00:00:00Z`; `--to 2026-11-30` → `ts < 2026-12-01T00:00:00Z`.
- `--from > --to` — невалидный диапазон: сообщение в stderr, exit 1, stdout пуст;
  равные даты допустимы (один полный день UTC).
- Порядок строк: `ORDER BY ts, id`.
- `ts` — RFC 3339 UTC с микросекундами (точность Postgres). `table_id NULL` → пустое поле
  (не строка «NULL»).
- `payload` — канонический текст jsonb как хранится в БД; поле в кавычках, экранирование
  по RFC 4180 (внутренние кавычки удваиваются).
- Кодировка UTF-8, разделитель строк LF, без BOM.
- Невалидное значение флага или недоступная БД: сообщение в stderr, exit 1, stdout пуст.

## 5. Приватность
- payload не содержит свободного ввода (его в v0 нет), имён, устройств, гео (AN-05).
- session_id — аналитический `sessions.id` (UUIDv4), не credential; table_id — номер столика
  (не персональные данные). Cookie-credential независим от session_id; ни он, ни его hash
  не попадают в JSON/CSV/логи. Схема CSV неизменна; даже исторический CSV UUID не даёт доступа
  к сессии/корзине после cutover: lookup по sessions.id и legacy fallback запрещены (ADR-0005).
