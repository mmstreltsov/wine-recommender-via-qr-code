# 60. Команда агентов: роли и правила взаимодействия (loop)

> Как устроена команда агентов: кто что пишет, кто что апрувит, как устроен цикл (loop),
> кто чем блокирует. Обязательно к прочтению каждым агентом перед первой задачей.
> Роли, помеченные `*`, добавлены координатором сверх исходного списка пользователя — не убирать.

## 1. Принципы

- Один артефакт — один автор. Правка чужой зоны — через loop (раздел 5), не напрямую.
- Контракты (`docs/30-contracts/`) и реестр (`docs/10-requirements.md`) меняются только через
  loop с апрувом; код следует за документом, не наоборот.
- Задача закрыта только явным «OK» каждого обязательного апрувера. Молчание не считается согласием.
- Условия закрытия вехи: все задачи OK + security-аудит без CRITICAL/HIGH + трассировка обновлена.

## 4. Право veto

| Роль | Область veto | Основание |
|---|---|---|
| Безопасник | любые артефакты | находки CRITICAL/HIGH блокируют закрытие вехи (`50-plan.md`) |
| Тестировщик | код и данные | красные тесты, непройденные acceptance-критерии, отсутствие трассировки на ID |
| Архитектор | `docs/30-contracts/`, структура системы | расхождение кода с контрактом, нарушение core/plugin-изоляции |
| Ревьюер требований | `docs/10-requirements.md` | неполный/противоречивый/нетестируемый реестр — веха не стартует |

Координатор veto не отменяет: он разрешает конфликты между ролями; снятие veto = устранение
находки либо явное решение пользователя по эскалации.

## 5. Loop — цикл взаимодействия агентов

### 5.1 Базовый цикл (задача)

1. Координатор формулирует задачу: цель, файлы, ID требований (FR/UI/AN/NFR), критерий
   готовности, список обязательных апруверов (по матрице 5.2).
2. Исполнитель реализует, сам прогоняет тесты/lint, передаёт на ревью.
3. Каждый апрувер возвращает findings одним списком: severity `BLOCKER/HIGH/MED/LOW`,
   `файл:строка`, готовая формулировка правки.
4. Исполнитель исправляет и отвечает по каждому пункту: «исправлено (файл:строка)» либо
   обоснованный отказ (отказ разрешает координатор).
5. Цикл 3–4 повторяется, пока все апруверы явно не ответят «OK». Молчание ≠ OK.
6. Координатор закрывает задачу; веха закрыта, когда все её задачи OK и security-аудит чист.

### 5.2 Матрица апрувов по типам артефактов

| Артефакт | Обязательные апруверы |
|---|---|
| Контракты `docs/30-contracts/` и другие доки | архитектор + ревьюер требований; `events.md`, `recommender.md` — дополнительно аналитик |
| Реестр `docs/10-requirements.md` | ревьюер требований + архитектор |
| Бэкенд-код (`backend/`) | тестировщик + безопасник; после каждой вехи — обязательный полный security-аудит |
| Фронтенд-код (`frontend/`) | тестировщик + безопасник (XSS, обработка внешних данных: CDN-фото, ответы API) |
| Данные и тексты рекомендаций (`data/aidabaran/recommender/`) | аналитик + тестировщик |
| Миграции БД | бэкенд (не автор правки) + безопасник |
| Деплой/инфра (compose, скрипты, VPS) | SRE + безопасник |
| ВКР-тексты и отчёты по вехам | техписатель + координатор |

### 5.3 Правила обмена информацией

- Findings — одним сообщением на итерацию, с severity и `файл:строка`; не по одному.
- Формулировки только конкретные: «замени X на Y в файле:строка». «Поправь, как считаешь
  нужным» запрещено.
- Ответ исполнителя — по каждому пункту списка, без пропусков.
- Расхождения между апруверами разрешает координатор; если не может — эскалация пользователю.

### 5.4 Лимит итераций и эскалация

- Максимум 3 цикла ревью на задачу.
- Если после 3-го цикла остаются BLOCKER/HIGH — эскалация пользователю: перечень разногласий,
  позиции сторон, варианты решения.

### 5.5 Anti-patterns

- Начинать веху без явного OK ревьюера требований.
- Считать задачу готовой по «тесты зелёные» без трассировки на ID требований.
- Мёржить конфликтные правки контрактов молча, без loop и апрува.
- Принимать молчание апрувера за OK.
- Findings без `файл:строка` и без готовой формулировки правки.
