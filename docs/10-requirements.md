# 10. Реестр требований — прототип v0

> Единственный источник правды о скоупе. Формат: ID · Приоритет (Must/Should/Won't) · требование ·
> acceptance-критерии (Given/When/Then) · источник. ID FR-01…FR-24 унаследованы из черновика ТЗ
> (пропуски 16/22 — исторические, из черновика). Новые — с FR-25.
> Колонка «Проверено» заполняется по мере реализации (traceability).

## 1. Общие

- **Скоуп:** гостевой сайт (меню → карточка → рекомы → корзина → заглушка оплаты) + сбор событий.
  Без админки, без реальной оплаты, без винного модуля (`docs/00-context.md`, О6).
- **Принцип «1 заказ — 1 рот»** (О3): корзина сессии — заказ одного человека.

| ID | Приоритет | Требование | Acceptance | Проверено |
|---|---|---|---|---|
| FR-01 | Must | Сайт содержит только раздел «Онлайн-меню»: без доставки, о ресторане, контактов и прочих разделов сайта ресторана | AC: в навигации/роутах отсутствуют любые страницы кроме `/`, `/dish/:id`, `/cart`, `/pay-stub` | |
| FR-02 | Must | Сохранены все категории меню ресторана (14 категорий из `data/aidabaran/menu.json`, порядок как на сайте) | AC: `GET /api/v1/menu` возвращает 14 категорий с названиями «Салаты»…«Напитки»; на экране видно все | |
| FR-03 | Must | Карточка каждого блюда открывается по нажатию | AC: клик/тап по любой карточке → роут `/dish/:id`, открывается экран карточки | |
| FR-04 | Must | Карточки выглядят интерактивно (пользователю понятно, что можно открыть): курсор-pointer, hover-состояние, визуальная целостность карточки-кнопки | AC: hover на десктопе подсвечивает карточку; tap-target ≥ 44px на мобильном | |
| FR-25 | Must | Фильтрация по категориям через чипы (как на сайте ресторана): активный чип жёлтый, по умолчанию «Все» | AC: тап по чипу «Хачапури» показывает только позиции категории; «Все» возвращает полный список; событие `category_select` отправлено | |
| FR-26 | Must | Фото блюда на карточке: primary — CDN ресторана с ресайзом `/-/resize/400x400/`, fallback — локальная копия через `onerror` | AC: при блокировке CDN (`photos[0]` → 404) карточка показывает локальный файл `photo_fallback` | |
| FR-27 | Should | В шапке экрана — название и логотип ресторана (из конфига), бейдж корзины со счётчиком позиций | AC: тап по бейджу открывает корзину; счётчик = суммарное количество позиций | |

## 4. Экран карточки блюда

| ID | Приоритет | Требование | Acceptance | Проверено |
|---|---|---|---|---|
| FR-05 | Must | Детальная карточка по аналогии с карточкой товара маркетплейса: большое фото сверху, название, цена, состав, лента рекомов; верхняя часть фиксирована по смыслу (фото → инфо → рекомы) | AC: экран содержит все блоки; скролл естественный, без горизонтального переполнения | |
| FR-06 | Must | Отображается стоимость блюда (в ₽) | AC: цена на экране = `price` из данных | |
| FR-07 | Must | Отображается состав блюда, если указан (КБЖУ и описание из `menu.json`): блок «Состав» показывается, если непусто `kbju` ИЛИ `description` | AC: у позиции с КБЖУ блок «Состав» виден; у позиции без КБЖУ, но с `description` — блок виден (только описание); при пустых обоих блока нет (не пустая заглушка) | |
| FR-08 | Won't (v1) | Дополнение состава через LLM — вторая итерация, в v0 не реализуется | — | |
| FR-09 | Must | Под карточкой — вертикальная лента рекомендаций | AC: блок рекомов расположен после блока состава, карточки в одну колонку | |
| FR-10 | Must | В ленте — топ-1 блюдо из каждой категории меню, сочетающееся с выбранным (кроме категории самого блюда; категория без подходящей пары — пропускается). Алгоритм выбора: `docs/30-contracts/recommender.md` | AC: для блюда «Хинкали» лента содержит по одной позиции из ≥5 разных категорий, ни одна — не из «Хинкали»; длина ленты = числу категорий с парой | |
| FR-11 | Must | У каждого рекомендованного — текст обоснования «почему хорошо дополняет» | AC: каждая карточка ленты содержит непустой текст ≥ 1 предложения | |
| FR-12 | Must | Тексты обоснований — гастрономические, в стилистике высокой кухни (аппетитно, конкретно, без «вкусно и просто»); контроль качества текстов — по примерам в `recommender.md` | AC: ревью текстов матрицы по чек-листу стиля (см. `docs/30-contracts/recommender.md` §тексты) | |
| FR-13 | Must | Основное блюдо визуально отделено от блока рекомендаций; у блока подзаголовок «Хорошо сочетается с» | AC: скриншот — блюдо и рекомы разделены; подзаголовок присутствует | |
| FR-14 | Must | Каждое рекомендованное можно добавить в корзину прямо из ленты (кнопка на карточке) | AC: тап «Добавить» на карточке ленты → бейдж корзины увеличился, событие `rec_add_click` записано, страница не перезагрузилась | |
| FR-15 | Must | Из ленты рекомов НЕЛЬЗЯ открыть детальную карточку рекомендованного (нет третьего уровня вложенности) | AC: тап по телу карточки ленты никуда не ведёт (кроме кнопки «Добавить») | |
| FR-28 | Must | В ленте не повторяются позиции, уже лежащие в корзине | AC: добавив позицию из ленты и вернувшись в карточку, её там больше нет | |
| FR-29 | Should | Если для блюда ни одна категория не дала пары (нет данных) — блок рекомов скрывается целиком; никаких пустых заглушек | AC: тестовый item без пар → блока нет, экран карточки валиден | |
| FR-30 | Must | Кнопка «Добавить в корзину» для самого блюда вверху карточки (рядом с ценой) | AC: тап → позиция в корзине, событие `menu_add_click` | |

## 5. Экран корзины

| ID | Приоритет | Требование | Acceptance | Проверено |
|---|---|---|---|---|
| FR-17 | Must | Корзина показывает все добавленные позиции (фото-превью, название, цена, количество) | AC: состав и суммы совпадают с добавленным; количество показывается, если > 1 | |
| FR-18 | Must | Удаление позиции — крестик в углу карточки позиции | AC: тап по крестику → позиция исчезла, сумма пересчитана, событие `cart_item_remove` | |
| FR-19 | Must | После списка позиций — блок с одной рекомендацией (топ-1) по текущему составу корзины. Алгоритм: `docs/30-contracts/recommender.md` | AC: блок «Хорошо сочетается с» содержит ровно одну карточку с обоснованием | |
| FR-20 | Must | Рекомендация меняется динамически при изменении состава корзины | AC: добавили десерт → реком (десертная пара) сменился; удалили всё → блок рекома исчез | |
| FR-21 | Must | Рекомендованная позиция может быть из любой категории (в т.ч. той, откуда в корзине уже есть позиции других блюд; исключая позиции, уже в корзине — FR-28) | AC: в тестах алгоритма рекомендация из категории, отсутствующей в корзине, приоритетнее | |
| FR-23 | Must | Кнопка «Оплатить» внизу корзины + итоговая сумма заказа | AC: сумма = Σ(цена×кол-во); кнопка видима всегда, при пустой корзине экран другой (FR-31) | |
| FR-24 | Must | Тап «Оплатить» → экран-заглушка с текстом «Позовите официанта, оплата через сайт временно не работает» | AC: роут `/pay-stub`, текст дословно такой; событие `pay_click` записано до перехода | |
| FR-31 | Must | Пустая корзина: экран с «Корзина пуста» и кнопкой возврата в меню; без кнопки «Оплатить» и блока рекома | AC: пустая корзина не содержит элементов оплаты/рекомов | |
| FR-32 | Must | Изменение количества: повторный «Добавить» той же позиции увеличивает количество (макс. 20); в корзине — степпер +/− | AC: qty меняется, сумма пересчитывается, событие `cart_qty_change` | |

## 6. Сессия, QR, анонимность

| ID | Приоритет | Требование | Acceptance | Проверено |
|---|---|---|---|---|
| FR-33 | Must | Анонимная сессия: сервер при первом запросе ставит UUID-cookie (HttpOnly, SameSite=Lax; Max-Age вычисляется из COOKIE_MAX_AGE_H, по умолчанию 12 ч); все события/корзина привязаны к session_id. Никаких ПДн (О1) | AC: в БД нет полей с персональными данными; cookie не читается из JS | |
| FR-34 | Must | QR-ссылка содержит столик: `/?table=N` (целое 1–999). Некорректный/отсутствующий `table` → работает без привязки (table_id = NULL в событиях) | AC: `/?table=12` → события с table_id=12; `/?table=abc` → NULL, сайт работает | |
| FR-35 | Must | Ошибки сети/сервера: дружелюбный экран «Что-то пошло не так, попробуйте ещё раз» + повтор; никаких стеков/кодов наружу | AC: при остановленном бэкенде фронт показывает экран повтора, без технических деталей | |

## 7. Аналитика (исследование проблемы)

| ID | Приоритет | Требование | Acceptance | Проверено |
|---|---|---|---|---|
| AN-01 | Must | Фиксированная таксономия событий (`docs/30-contracts/events.md`): никаких «произвольных» названий | AC: все события в БД ∈ списку таксономии | |
| AN-02 | Must | Любые значимые клики/просмотры записываются (перечень — в events.md: просмотры, открытия карточек, показы рекомов, клики добавления, действия корзины, оплата) | AC: ручной прогон полного пути гостя создаёт все ожидаемые события | |
| AN-03 | Must | Каждое событие содержит: session_id, table_id (NULL, если сессия без столика), timestamp, payload по схеме | AC: строки в `events` заполнены; payload валиден по схеме | |
| AN-04 | Must | Выгрузка для исследования: `server export-events --from 2026-11-01 --to 2026-11-30 > events.csv` (ts, session_id, table_id, name, payload) | AC: CSV открывается, колонки соответствуют, кодировка UTF-8 | |
| AN-05 | Must | Без ПДн в событиях: payload не содержит свободного ввода гостя (его в v0 нет вовсе) | AC: ревью схемы payload'ов — только ID и служебные поля | |

## 8. Нефункциональные

| ID | Приоритет | Требование | Acceptance | Проверено |
|---|---|---|---|---|
| NFR-01 | Must | Mobile-first: основной сценарий — телефон из QR (iOS Safari, Android Chrome); сетка колонок — по таблице брейкпоинтов из `docs/40-frontend.md` | AC: на 375px нет горизонтального скролла, все tap-targets ≥ 44px | |
| NFR-02 | Should | Скорость: первый экран интерактивен < 2.5s на 4G; фото ленивые, CDN-ресайз (не оригиналы 700КБ) | AC: Lighthouse performance ≥ 70 на профиле Slow 4G | |
| NFR-03 | Must | Без авторизации и без форм ввода данных гостя | AC: в UI нет ни одной формы ввода | |
| NFR-04 | Must | Безопасность: параметризованные запросы, валидация входа (item_id существует, qty 1–20, table 1–999), rate-limit на events (анти-спам); кросс-доменные запросы не поддерживаются; все запросы same-origin (дев — через vite-proxy) | AC: security-аудит вехи без CRITICAL/HIGH | |
| NFR-05 | Should | Весь стек поднимается `docker compose up` (postgres + backend + статика фронта) | AC: на чистой машине одна команда поднимает работающий сайт на :8080 | |
| NFR-06 | Must | Все UI-тексты на русском языке | AC: ревью строк интерфейса | |
