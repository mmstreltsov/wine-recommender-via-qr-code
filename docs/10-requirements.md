# 10. Реестр требований — прототип v0

> Единственный источник правды о скоупе. Формат: ID · Приоритет (Must/Should/Won't) · требование ·
> acceptance-критерии (Given/When/Then) · источник. ID FR-01…FR-24 унаследованы из черновика ТЗ
> (пропуски 16/22 — исторические, из черновика). Новые — с FR-25.
> Колонка «Проверено» заполняется по мере реализации (traceability).

## 1. Общие

- **Скоуп:** гостевой сайт (меню → карточка → рекомы → корзина → заглушка оплаты) + сбор событий.
  Без админки, без реальной оплаты, без винного модуля (`docs/00-context.md`, О6).
- **Принцип «1 заказ — 1 рот»** (О3): корзина сессии — заказ одного человека.

## 7. Учёт наличия блюд (availability)

Проблема: онлайн-меню больше фактического предложения зала (визит в пилот) — гость должен
видеть, заказывать и получать рекомендации только по доступным позициям. Решение — ADR-0006.

| ID | Приоритет | Требование | Acceptance | Проверено |
|---|---|---|---|---|
| FR-36 | Must | Учёт наличия блюд: таблица Postgres `item_availability` (`item_id BIGINT PK`, `is_available BOOLEAN NOT NULL`, `updated_at`; без FK — меню статика в памяти, `item_id` валидируется CLI против меню из `DATA_DIR`). Семантика default-available: отсутствующая строка = позиция доступна (при старте всё доступно, отключения вносит заказчик). Чтение сервером — in-memory множество недоступных `item_id` с TTL-обновлением, env `AVAILABILITY_TTL_S` (по умолчанию 5 с): изменения подхватываются без рестарта в пределах TTL. Управление — CLI-подкоманда того же бинаря, без HTTP, по образцу `export-events`: `go run ./cmd/server availability set <item_id> on\|off` (upsert) и `availability list` (текущие отключения: по строке `item_id available=off updated_at` в UTC ISO 8601, нет отключений — строка «нет отключений»); плюс `availability find <подстрока названия>` — печать совпавших позиций меню (`uid`, название, категория, `on/off`), чтобы не искать uid вручную; работает с той же БД при живом сервере. При ошибке обновления TTL-кэша (БД недоступна) сервер работает по последнему успешно загруженному срезу и логирует ERROR | AC: (а) `availability set <item_id> off` при живом сервере → позиция исчезает из `GET /menu` в пределах TTL, без рестарта; (б) `set off`/`set on` (upsert) и `list` работают при живом сервере; (в) нет строк в таблице = все позиции доступны; (г) `availability find <подстрока>` печатает все совпадения в формате uid/название/категория/on-off, без совпадений — «ничего не найдено» | да: item_availability + TTL-кэш (default-available, stale-while-revalidate, не блокирует запросы); CLI set/list/find при живом сервере: off исчезает из /menu в пределах TTL (0.34с при TTL 2с) без рестарта; ошибка БД → последний срез + ERROR (TestFR36_*, live-прогон а–г); клиентски (M4): off при живом сервере подхватывается без рестарта (линия muted в корзине после TTL), on восстанавливает (375+1440) |
| FR-37 | Must | Фильтрация недоступных (`is_available=false`) во всех выдачах: (1) `GET /menu` — недоступные позиции исключаются, категории без оставшихся позиций исключаются целиком (с `category_id` — чипы пустых категорий не показываются); (2) `GET /menu/items/{id}` и `…/{id}/recommendations` недоступной позиции → `404` (как несуществующая); (3) полный `MenuItem`: из `upsell_options` исключаются недоступные опции; (4) `POST /cart/items` с недоступной позицией → `409 item_unavailable` (в теле ошибки `item_id`); (5) `GET /cart`: каждая линия получает поле `available: bool`; (6) `PATCH`/`DELETE /cart/items/{id}` работают как обычно (недоступную можно удалить, qty менять не запрещено); (7) оплата (заглушка FR-24): серверной операции оформления заказа в v0 НЕТ — блокировка фронтовая (UI-04): при линиях `available=false` кнопка «Оплатить» показывает сообщение, перехода на `/pay-stub` и событий `pay_click`/`stub_view` нет;
