# 00. Контекст продукта — «Свое Шеф»

> Этот файл — самодостаточный конденсат проекта. Внешние материалы команды (бриф, PSW, дерево
> гипотез, расшифровки звонков) НЕ нужны для разработки: всё значимое собрано здесь.

## Что строим

QR-код на столике ресторана → гость сканирует → в браузере телефона открывается **онлайн-меню
ресторана** с рекомендациями: «что ещё заказать к выбранному блюду / к текущей корзине».
Каждая рекомендация — с коротким гастрономическим обоснованием. Корзина → кнопка «Оплатить» →
заглушка («позовите официанта»). Сервис собирает анонимную воронку событий для исследования.

- **Заказчик:** РСХБ (экосистема «Свое»), учебный проект команды ВКР. Продукт бесплатен для ресторана.
- **Зачем ресторану:** рост среднего чека (дозаказы) без затрат на персонал.
- **Зачем банку:** повод зайти в рестораны (счёт + эквайринг — монетизация банка, не наша забота).

## Ключевая боль (гипотеза, проверяется исследованием)

Гость не знает, что заказать в дополнение к блюду; официант/сомелье физически не успевает к каждому
столу → гость берёт только основное → чек низкий. Окно возможности: **~15 минут ожидания заказа**.
Проект НЕ доказал эту боль заранее — прототип нужен в том числе чтобы собрать данные (воронка,
доля дозаказов) для проверки гипотез П1–П5 (гипотезы проблемы: гость не знает, что заказать
в дополнение; официант не успевает подсказать).

## Метрики успеха (пилот)

1. Рост среднего чека ресторана (ориентир заказчика: +10%).
2. Доля гостей, дозаказавших по рекомендации (воронка ниже).
3. A/B: QR не на всех столиках, сравнение столиков с QR/без → поэтому `table_id` в ссылке QR.

Воронка исследования: `page_open → menu_view → dish_card_open → rec_impression → rec_add_click →
cart_* → pay_click`. Полная таксономия: `docs/30-contracts/events.md`.

## Жёсткие ограничения (нарушать нельзя)

| # | Ограничение |
|---|---|
| О1 | **Никаких ПДн**: нет логина, профилей, «запоминания гостя». Анонимная сессионная аналитика разрешена |
| О2 | Рекомендуем только позиции из меню этого ресторана |
| О3 | «1 заказ — 1 рот»: заказ в сессии — для одного человека (никакого «общего стола») |
| О4 | v0 без ML и без рантайм-LLM: рекомендации = экспертные правила + эвристики, тексты — статический контент. Это решение скоупа v0, не вечный запрет: рантайм-LLM — допустимая опция v1+ (отдельный ADR) |
| О5 | Масштабируемость «как Лего»: ядро без специфики ресторана; специфика — в подключаемом модуле |
| О6 | Прототип v0 — только гостевой сайт. Без админ-UI, без оплаты, без винного модуля (вино — позже); CLI управления наличием блюд — в v0 (FR-36) |
| О7 | Границы заказчика: только «помощник за столом». Закупки, сети, чаевые, бронирования — чужие зоны |

## Пилотный ресторан: АйДаБаран (aidabaran.ru)

Несетевой авторский, грузинская + европейская кухня, Москва. Данные собраны и лежат в `data/aidabaran/`:

- `menu.json` — 125 позиций кухни, 14 категорий, цены 150–4500₽ (медиана 650₽). У каждой позиции:
  название, цена, описание (вес), КБЖУ (89/125 позиций с КБЖУ; 7 null; 28 напитков с
  текстом-описанием вместо КБЖУ), фото (проф. съёмка), у 16 позиций —
  апсейл-опции ресторана («добавьте в салат креветки +420₽»).
- `barmenu.json` — 251 позиция бара (OCR фото винной карты). **В v0 не используется** — файл в репо
  для будущего винного модуля.
- `assets/tokens.css` — дизайн-токены с их сайта: шрифты Unbounded (заголовки) + Montserrat (текст),
  палитра чёрный/белый/жёлтый `#fdc300`, радиусы 10px.
- Фото: основной источник — CDN Тильды ресторана (CORS открыт, ресайз на лету
  `/-/resize/400x400/`), fallback — локальные копии (`python3 parser.py photos`, см.
  `data/aidabaran/README.md`). Поведение фото на фронте — `docs/40-frontend.md`.

## Принятые решения (почему так)

| Решение | Обоснование |
|---|---|
| Веб в браузере, без установки/логина | QR → мгновенный доступ, нет магазина приложений |
| Core без специфики ресторана + плагин | О5; проверено требованием масштабируемости из звонков |
| Рекомы: матрица пар + эвристики категорий | О4; данных о заказах нет, коллаборативная фильтрация невозможна |
| Тексты обоснований — статика | О4; пишутся оффлайн (аналитик + LLM-черновики), в рантайме только подстановка |
| Cart и события в Postgres, меню в памяти | Меню статично; динамика нужна для аналитики исследования |
| Без админки | Для сбора данных исследования достаточно воронки кликов; подтверждение дозаказов — позже. «Без админки» = без админ-UI; операционное управление (наличие блюд) — CLI (FR-36) |
| Наличие блюд: `item_availability` + CLI `availability` (FR-36/37) | Онлайн-меню ≠ фактическое предложение зала (выяснено визитом в пилот): отсутствующие позиции скрываются оперативно, без релиза и рестарта (ADR-0006) |
| Рекомы из любых категорий (не только вино) | Скоуп v0 согласован: сначала любые блюда, винный модуль — отдельная итерация |

## Пользовательский путь (v0)

1. Сканирует QR (`https://…/?table=N`) → онлайн-меню (категории = как у ресторана).
2. Открывает карточку блюда (как карточка товара маркетплейса): цена, состав, лента рекомендаций
   «Хорошо сочетается с» — топ-1 из каждой категории, у каждой — обоснование, добавление в корзину
   прямо из ленты.
3. Корзина: список, удаление, динамическая топ-1 рекомендация по составу корзины, сумма.
4. «Оплатить» → заглушка «Ваш выбор сформирован. Позовите официанта.».

## Вне скоупа v0 (не строить)

Винные рекомендации и барная карта, админ-UI ресторана (управление наличием блюд в v0 — CLI,
FR-36), подтверждение дозаказов официантом,
реальная оплата/эквайринг, A/B-переключение фич на бэкенде, профили гостя, интеграция с POS,
LLM-дополнение составов (FR-08), промо/тайм-офферы, чат-сомелье.
